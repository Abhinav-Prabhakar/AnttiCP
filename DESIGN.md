# Design & build rules — *Guide to Competitive Programming*, interactive edition

This document is the contract for every chapter page. Read it fully before writing.
Chapter 01 (`index.html`, `chapters/ch01.body.html`, `chapters/ch01.css`, `chapters/ch01.js`)
is the reference implementation. If in doubt, match it.

---

## 1. What we are building

A complete, white-background, editorial web edition of all fifteen chapters of
Antti Laaksonen's *Guide to Competitive Programming*.

Each chapter is a standalone page with the same shell:

- fixed top bar (book mark, chapter label, reading progress, contents)
- left section rail (generated from your sections)
- chapter hero
- chapter sections
- a generated end-of-chapter block linking to the next chapter
- a contents drawer listing every chapter and the current chapter's sections

The shell is generated by `build.mjs`. **You do not write the shell.**

The tone is calm, precise, book-like. It should feel designed by a human editor,
not generated. Every chapter must carry the same level of care as Chapter 01:
strong typography, generous whitespace, bespoke diagrams, restrained motion,
and at least one genuinely interactive explanation.

---

## 2. Files you own — do not touch anything else

For chapter `NN`, create exactly these three files:

```
chapters/chNN.body.html   the page content fragment
chapters/chNN.css         chapter-specific styles
chapters/chNN.js          chapter-specific interactions
```

Never edit: `index.html`, `styles.css`, `shared.js`, `build.mjs`, `book.json`,
`chapters/_sprite.html`, `chapters/_template.body.html`, `source/**`, or any
other chapter's files.

### Body fragment

- Starts with `<section class="hero" ...>`.
- Ends after your last `</section>`.
- No `<!DOCTYPE>`, `<html>`, `<head>`, `<body>`, `<main>`, `<header>`, `<footer>`,
  drawer, icon sprite, `<style>`, or `<script>` tags.
- Every content section follows the shared pattern:

```html
<section class="section" id="s21" aria-labelledby="h21">
  <div class="wrap">
    <div class="section-head" data-reveal>
      <span class="section-num">2.1</span>
      <div class="section-head__body">
        <h2 id="h21">Language Features</h2>
      </div>
    </div>
    ...content...
  </div>
</section>
```

- Sub-sections use `class="section section--sub"` and one deeper number, e.g. `2.1.1`
  with `id="s211"`.
- Keep IDs unique and stable: `s21`, `s211`, `s22`, ...
- The build script reads `.section-num` and the first `<h2>` to generate the rail
  and drawer. Do not omit them.
- Do not add a second `<h1>`; the hero owns it.

### CSS

- Prefix **every new class** with `chNN-` (e.g. `.ch02-stack`, `.ch07-grid`).
- You may extend shared classes with a chapter-scoped selector
  (`.ch02 .chips { ... }`) but do not redefine shared classes globally.
- No `@font-face`, `@import`, external URLs, or libraries.
- Use the design tokens (section 4). No hard-coded new font stacks.
- All custom CSS must be responsive; add your own media queries if needed.

### JS

- Wrap everything in an IIFE (or use a top-level `const` block) and scope every
  selector to `.chapter`-content ids/classes.
- Guard every query (`if (!el) return;`). The script runs after the DOM.
- Use `window.CP` helpers instead of adding libraries.
- Keep it dependency-free, deterministic and seek-safe (no infinite layout thrash).

## 3. Where the content comes from

- Extracted text: `source/text/chNN.txt` (PDF page markers included).
- Page images: `source/pages/pNNN.png` (300 dpi-ish renders, useful for figures/tables).
- The chapter's section list is in `book.json`'s sibling TOC and in the brief.

Rules:

- Cover **every section** of the chapter. Do not skip a section because it is
  mathematical or code-heavy.
- Condense for the web; do not paste walls of text. One clear paragraph plus a
  visual often beats three paragraphs.
- Prefer the book's own examples, algorithms, pseudocode, and problem names.
- Never invent facts, quotations, complexity results, or historical claims.
- Code must be correct and runnable in the language shown. Use C++ as the
  primary language, matching the book; add other languages only where it helps.
- Use proper mathematical notation in HTML (`<i>n</i>`, `<sup>2</sup>`, `O(n log n)`
  with `<i>`), never images of formulas.

## 4. Visual language

### Palette and type

Use the shared tokens in `styles.css`:

| token | value | use |
|---|---|---|
| `--ink` | `#171717` | headings, primary text |
| `--body` | `#3a3a36` | long-form body |
| `--muted` | `#77776f` | secondary text |
| `--faint` | `#a6a69e` | metadata, captions |
| `--line` | `#ecece7` | rare hairlines |
| `--line-soft` | `#f4f4f0` | very rare separators |
| `--wash` | `#f8f8f5` | soft panels/visual beds |
| `--wash-2` | `#f1f1ec` | second surface, fills |
| `--signal` | `#a6402e` | a single warning/error accent |
| `--serif` | Newsreader | display, body, captions |
| `--sans` | Inter | labels, UI, kickers |
| `--mono` | JetBrains Mono | code, numbers, tiny metadata |

### Typography hierarchy

- Hero `h1`: `clamp(...)`, Newsreader 300, letter-spacing around `-.04em`.
  Chapter 01 uses 176px at 1440. Long titles must be reduced — add a
  `chNN-hero--long` class and set `font-size: clamp(48px, 8vw, 108px)`.
- Section `h2`: default from `.section-head h2` (`clamp(38px, 4.8vw, 62px)`),
  Newsreader 300.
- Sub-section `h2`: use `.section-head--sub h2` (smaller).
- Lead: `.lead` (20px) or `.statement` for the one big idea.
- Body: global 18.5px/1.66.
- Kickers: `.kicker` (Inter 9px, uppercase, tracked).
- Numbers/data: `--mono`, tabular.

### Layout

- Page width: `.wrap` (1180px max, 40px pad; 20px at 640).
- Section rhythm: `.section` handles vertical padding. Do not add huge margins
  between sections.
- Starting pattern for every chapter:
  1. Hero: eyebrow (`Chapter NN` / title), h1, lead, meta line
     (`N sections · N pages · ≈ N min`), one bespoke hero diagram.
  2. Optional chapter index (`.chapter-index`) for chapters with 3+ sections.
  3. Sections, alternating prose/visual rhythm.
- Visual blocks sit in `--wash` beds with rounded 3px corners, never in outlined
  cards. Use `.figure`, `.figure__frame`, `.figure__cap` for consistency.

### What to avoid

- Heavy black borders, boxed-in sections, "dashboard card" grids.
- Purple gradients, glows, glassmorphism, drop shadows (except a 6–16px lift on
  hover), emoji, stock images, icon soup.
- More than one solid-black block per chapter (the generated end card does not
  count). Black is an accent, not a surface.
- Decorative diagrams that do not explain the text.
- Long paragraphs with no visual break.
- Tiny grey text below 9px except metadata labels.

### Motion

- Reveal content with `data-reveal`; the shell observes it and adds `.is-visible`.
  Add `style="--d:.08s"` for stagger.
- Use `var(--ease)` (`cubic-bezier(.22,1,.36,1)`) for entrances and
  `var(--ease-io)` for loops.
- Durations 180–500ms; nothing longer than 700ms except a deliberate plot draw.
- Hover/tap details must also work with keyboard focus.
- No scroll-jacking, parallax, or autoplaying audio.
- Respect `prefers-reduced-motion`: the global CSS already neutralises
  animations; make sure your JS does not depend on a transition to work.

## 5. Required richness per chapter

Every chapter must include, at minimum:

1. A bespoke hero visual (SVG or CSS) that captures the chapter's central idea.
2. **At least three** custom explanatory visuals across the chapter. Examples:
   - dot grids / matrices / trees / graphs / arrays
   - before/after comparisons
   - timelines, step machines, bar/line plots
   - code traces with highlighted state
   - geometric constructions
3. **At least one interaction** that changes what the reader sees:
   tabs, a slider, a stepper, a toggle, a hover-to-inspect diagram, a small
   simulator. It must teach something, not just animate.
4. **One piece of secondary data tucked behind hover/tap/focus** (a `data-tip`
   tooltip, a details/summary note, or a hover-revealed readout).
5. One code/algorithm block where the source has code, using the shared code
   card and syntax highlighting.
6. At least one moment of restrained motion beyond the reveal (draw-on, count-up,
   travelling marker, morph, etc.).
7. A short closing idea that hands off to the next chapter — the shell adds the
   end card; your last section should still land the chapter.

Do not pad. A chapter with three strong visuals beats one with ten weak ones.

## 6. Shared components and helpers

### Section head

```html
<div class="section-head" data-reveal>
  <span class="section-num">2.1</span>
  <div class="section-head__body"><h2 id="h21">Language Features</h2></div>
</div>
```

### Prose

```html
<p class="statement" data-reveal>One big idea…</p>
<p class="lead" data-reveal>Supporting paragraph…</p>
```

### Figure / visual bed

```html
<figure class="figure" data-reveal>
  <div class="figure__frame">
    <svg viewBox="0 0 640 300" role="img" aria-label="…">…</svg>
  </div>
  <figcaption class="figure__cap">What the reader should notice.</figcaption>
</figure>
```

`figure__frame` can hold CSS-only diagrams too. Keep labels at 9–11px on screen;
inside an SVG use a viewBox scaled to the frame, not fixed pixel text.

### Two-column split

```html
<div class="split2"> <div>…</div> <div>…</div> </div>
```

Also `.split2--wide` (1.25fr / .75fr) and `.split2--narrow`.

### Chips, tags, stats

```html
<ul class="chips"><li class="chip chip--static">O(n log n)</li></ul>
<span class="tag">Binary search</span>
<div class="statline"><div><span class="statline__value">O(n)</span><span class="statline__label">time</span></div>…</div>
```

### Details note

```html
<details class="note">
  <summary><span class="note__label">Why this works</span><svg class="icon"><use href="#i-chevron"/></svg></summary>
  <div class="note__body"><p>…</p></div>
</details>
```

### Code card

```html
<div class="code-card" data-code-card>
  <div class="code-card__head">
    <div class="code-tabs" role="tablist" aria-label="Language" data-code-tabs></div>
    <div class="code-card__meta">
      <span class="code-card__file" data-code-file></span>
      <button class="copy-btn" type="button" data-code-copy aria-label="Copy code">
        <svg class="icon"><use href="#i-copy"/></svg><span>Copy</span>
      </button>
    </div>
  </div>
  <pre class="code" data-code-block><code data-code-lines></code></pre>
  <div class="code-card__foot">
    <p data-code-note></p><span class="code-card__hint" data-code-type></span>
  </div>
</div>
```

In `chNN.js`:

```js
const card = CP.mountCodeCard(document.querySelector('[data-code-card]'), {
  storageKey: 'gtcp-lang-ch02',
  order: ['cpp', 'python'],
  initial: 'cpp',
  langs: {
    cpp: {
      label: 'C++', file: 'example.cpp', type: 'O(n log n)',
      note: 'Sorts the array and scans it once.',
      pre: true,
      keywords: ['for', 'while', 'if', 'else', 'return', 'int', 'vector', 'sort'],
      types: ['int', 'long long', 'vector', 'bool'],
      code: [
        '#include <bits/stdc++.h>',
        'using namespace std;',
        'int main() { /* … */ }'
      ]
    },
    python: {
      label: 'Python', file: 'example.py', type: 'O(n log n)',
      note: 'The same idea in Python.',
      keywords: ['for', 'while', 'if', 'else', 'return', 'in', 'not', 'and', 'or'],
      types: ['int', 'list', 'dict'],
      code: ['data = sorted(map(int, input().split()))']
    }
  }
});
```

`CP.mountCodeCard` handles tabs, keyboard arrows, persistence, highlighting and
copy. Use it for every multi-language block. For a single static code block you
may write `<pre class="code"><code>…</code></pre>` manually, but keep the
`code`/`code-line` classes for line numbers.

### Tooltips (hidden secondary data)

```html
<circle data-tip="Range 2–5 · sum 14" tabindex="0" … />
```

The shared shell shows tooltips on hover and focus. Always give a keyboard target.

### Helpers

```js
CP.$ , CP.$$, CP.clamp, CP.fmt, CP.reduceMotion
CP.highlightCode(line, cfg)
CP.mountCodeCard(root, config)
CP.countUp(el, target, duration)
CP.onVisible(el, cb, {threshold})
CP.showTip(el) / CP.hideTip(el)
```

## 7. Interaction patterns that fit the book

Reuse these archetypes; vary the details:

- **Stepper / trace**: click or step through an algorithm; highlight the current
  line, array cell, or tree node.
- **Slider**: change n, k, a probability, or a threshold; update a chart, a
  complexity line, or a result.
- **Toggle / segmented control**: switch between two algorithms, two data
  structures, or two interpretations; cross-fade the diagram.
- **Hover-to-inspect**: nodes, cells, bars or ranges reveal their value; keyboard
  focus mirrors hover.
- **Build-up**: a button adds the next edge/cell/level, with a reset.
- **Compare**: two panes showing naive vs efficient, or before vs after.

Every interaction must have a visible initial state, a reset, and accessible
labels. Do not require drag on touch; provide buttons or a range input.

## 8. Responsive rules

- Test at 1440, 1024, 768, 393 and 320px.
- At ≤920px, two-column layouts collapse. Use `.split2` (already collapses) or
  your own media query. Diagrams should stack, not shrink to illegibility.
- At ≤640px: code cards keep tabs on their own row; code scrolls horizontally;
  no element may push the page wider than the viewport.
- SVG: always `viewBox`, `width: 100%`, `height: auto`. Hide non-essential labels
  at narrow widths instead of letting them collide.
- Do not use fixed heights that clip content; use `min-height` or aspect ratios.

## 10. Non-negotiables

- **Never edit shared or other chapters' files.**
- **Never add a dependency or an external request.**
- **Never use placeholders** (`Lorem`, `TODO`, "Coming soon") in the final page.
- Keep the design quiet. If a border or a black box is not doing real work,
  remove it.
- The chapter must feel finished, not scaffolded.
