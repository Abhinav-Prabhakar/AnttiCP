Dynamic Programming

An algorithm design technique for finding optimal solutions and counting them — by combining the answers to smaller subproblems, each computed only once.

6.1

Basic Concepts

Given a set of coin values and a target sum, use as few coins as possible. The obvious strategy is greedy — and it is wrong.

Suppose we are given coin values coins = {c1, c2, …, ck} and a target sum n, and asked to construct n with as few coins as possible. There is no limit on how often we use each coin value. For example, with coins = {1, 2, 5} and n = 12, the optimum is 5 + 5 + 2 = 12, three coins. The problem is small enough to see the whole idea of dynamic programming, and rich enough to need it.

The coin problem coins may repeat

coins = {c1, c2, …, ck}, target n. Construct the sum n with the minimum number of coins.

coins 125 n = 12 552 3 coins

There is a simple greedy algorithm, but it does not always produce an optimal solution. Using dynamic programming, we can create an efficient algorithm that always finds one.

6.1.1

When Greedy Fails

There is a natural greedy algorithm: always select the largest coin that keeps the sum within the target. For example, if n = 12, we select two coins of value 5, then one of value 2, which completes the solution. This looks like a reasonable strategy, but is it always optimal?

It turns out that this strategy does not always work. For example, if coins = {1, 3, 4} and n = 6, the optimal solution has two coins (3 + 3 = 6), but greedy produces three (4 + 1 + 1 = 6).

This simple counterexample shows that greedy is not correct. How could we solve the problem, then? We could look for another greedy algorithm, but there are no other obvious strategies to consider.

Why not try every combination?

Another possibility is a brute force algorithm that goes through all possible ways to select coins. It would surely give correct results, but be very slow on large inputs.

Using dynamic programming, we can create an algorithm that is almost like brute force but also efficient. Thus we can be sure it is correct and still use it on large inputs. Furthermore, the same technique solves a large number of other problems.

6.1.2

Finding an Optimal Solution

To use dynamic programming, we formulate the problem recursively, so that its solution follows from solutions to smaller subproblems. In the coin problem, a natural recursive problem is the function solve(x): what is the minimum number of coins required to form a sum x?

Clearly, the values of solve depend on the coin values. For example, if coins = {1, 3, 4}, the first values are solve(0) = 0, 1, 2, 1, 1, 2, 2, 2, 2, 3, 3. The essential property of solve is that its values can be calculated recursively from smaller values. The idea is to focus on the first coin we choose for the sum. In the above scenario, that coin can be 1, 3 or 4. If we first choose 1, the remaining task is to form the sum 9 using the minimum number of coins, a subproblem of the original. The same applies to coins 3 and 4. Thus we can use the following recursive formula.

The recursive definition solve(x)
x < 0∞impossible
x = 00the empty sum
x > 0 minc ∈ coins solve(x − c) + 1 try every first coin

For example: solve(10) = solve(7) + 1 = solve(4) + 2 = solve(0) + 3 = 3.

Plain recursion exponential 
int solve(int x) {
  if (x < 0) return INF;
  if (x == 0) return 0;
  int best = INF;
  for (auto c : coins) {
    best = min(best,
      solve(x - c) + 1);
  }
  return best;
}
With memoisation O(nk) 
int solve(int x) {
  if (x < 0) return INF;
  if (x == 0) return 0;
  if (ready[x]) return value[x];
  int best = INF;
  for (auto c : coins) {
    best = min(best,
      solve(x - c) + 1);
  }
  ready[x] = true;
  value[x] = best;
  return best;
}

The added lines are the whole idea. The function handles the base cases x < 0 and x = 0 as before. Then it checks ready[x] to see whether solve(x) is already stored in value[x], and if so returns it directly. Otherwise it calculates solve(x) recursively and stores the result in value[x]. This works efficiently, because the answer for each x is calculated only once. The time complexity is O(nk), where n is the target sum and k the number of coins.

Iterative implementation

We can also construct the array value iteratively with a loop. Most competitive programmers prefer this implementation, because it is shorter and has smaller constant factors. From now on, our examples use iterative implementations. Still, it is often easier to think about dynamic programming in terms of recursive functions.

Constructing a solution

Sometimes we are asked both to find the value of an optimal solution and to show how one can be constructed. In the coin problem, we can declare an array that indicates, for each sum, the first coin in an optimal solution. The following code prints the coins in an optimal solution for the sum n.

while (n > 0) {
  cout << first[n] << "\n";
  n -= first[n];
}

6.1.3

Counting Solutions

Let us consider another variant of the coin problem: counting the number of ways to produce a sum x using the coins.

For example, if coins = {1, 3, 4} and x = 5, there are 6 ways. Again, we can solve the problem recursively. Let solve(x) denote the number of ways to form the sum x. With coins = {1, 3, 4}, solve(5) = 6 and the recursive formula is solve(x) = solve(x − 1) + solve(x − 3) + solve(x − 4).

Often the number of solutions is so large that we only need it modulo m, where, for example, m = 109 + 7. We can do this by making all calculations modulo m. In the above code, it suffices to add the line count[x] %= m; after count[x] += count[x-c];

count[0] = 1;
for (int x = 1; x <= n; x++) {
  for (auto c : coins) {
    if (x - c >= 0) {
      count[x] += count[x - c];
      count[x] %= m;
    }
  }
}

6.2.1

Longest Increasing Subsequence

The longest increasing subsequence in an array of n elements is a maximum-length sequence that goes from left to right, each element larger than the previous one.

We can find the longest increasing subsequence efficiently using dynamic programming. Let length(k) denote the length of the longest increasing subsequence ending at position k. To calculate length(k), find a position i < k with array[i] < array[k] and length(i) as large as possible. Then length(k) = length(i) + 1, the optimal way to append array[k] to a subsequence. If there is no such position, length(k) = 1, and the subsequence only contains array[k].

6.2.2

Paths in a Grid

Our next problem is to find a path from the upper-left to the lower-right corner of an n × n grid, moving only down and right. Each square contains an integer, and the path should maximize the sum of values along it.

Assume the rows and columns are numbered from 1 to n, and value[y][x] is the value of square (y, x). Let sum(y, x) be the maximum sum on a path from the upper-left corner to (y, x). Then sum(n, n) is the maximum sum to the lower-right corner. The formula rests on the observation that a path ending at (y, x) comes either from (y, x−1) or from (y−1, x). Thus we select the direction that maximizes the sum.

best sum path selected
The recurrence

sum(y, x) = max(sum(y, x−1), sum(y−1, x)) + value[y][x]

Select any square to see the path that reaches it.

We assume that sum(y, x) = 0 if y = 0 or x = 0, so the recursive formula also works for leftmost and topmost squares.

Since sum has two parameters, the dynamic programming array has two dimensions. The time complexity is O(n2).

for (int y = 1; y <= n; y++) {
  for (int x = 1; x <= n; x++) {
    sum[y][x] = max(sum[y][x-1],
                    sum[y-1][x])
                + value[y][x];
  }
}
6.2.3

Knapsack Problems

The term knapsack refers to problems where a set of objects is given and subsets with certain properties must be found. Such problems can often be solved using dynamic programming. Here we focus on the following: given a list of weights [w1, w2, …, wn], determine all sums that can be constructed using the weights.

To solve the problem, we focus on subproblems that use only the first k weights. Let possible(x, k) = true if we can construct a sum x using the first k weights, otherwise false. The values can be calculated recursively with the formula below, based on whether we use the weight wk in the sum. If we use wk, the remaining task is to form x − wk from the first k − 1 weights; if not, it is to form x from the first k − 1 weights.

The transition possible(x, k)

possible(x, k) = possible(x − wk, k − 1) or possible(x, k − 1)

The base cases are possible(x, 0) = true if x = 0, false otherwise, because with no weights we can only form the sum 0. Finally, possible(x, n) tells us whether we can construct a sum x using all weights.

Weights [1, 3, 3, 5] · total 12 ✓ constructible

Row k uses only the first k weights. Row 2, for instance, shows that [1, 3] can construct 0, 1, 3, and 4. Hover a column heading to see one subset that makes that sum.

One array is enough

There is also a more compact way to implement the calculation, using one array possible[x] that indicates whether we can construct a subset with sum x. The trick is to update it from right to left for each new weight.

Let m denote the total sum of the weights. The two-dimensional version takes O(nm) time. The same idea applies to other knapsack problems, such as finding a maximum-value subset whose weight does not exceed a given limit.

possible[0] = true;
for (int k = 1; k <= n; k++) {
  for (int x = m - w[k]; x >= 0; x--) {
    possible[x + w[k]] |= possible[x];
  }
}
Why right to left?

Updating from the largest sum downwards means possible[x] still refers to the state before the current weight was added. Going the other way, the weight could be used again in the same pass.

6.2.4

From Permutations to Subsets

Using dynamic programming, we can often change an iteration over permutations into one over subsets. The benefit is that n!, the number of permutations, is much larger than 2n, the number of subsets. For example, if n = 20, n! ≈ 2.4 × 1018 and 2n ≈ 106. Thus, for certain n, we can go through the subsets efficiently but not the permutations.

As an example, consider an elevator with maximum weight x and n people who want to get from the ground floor to the top floor. The people are numbered 0, 1, …, n − 1, and person i has weight weight[i]. What is the minimum number of rides needed to get everybody to the top floor? The problem can be solved in O(n!n) time by testing all permutations of the n people. However, dynamic programming gives a more efficient O(2nn) algorithm. The idea is to calculate for each subset two values: the minimum number of rides and the minimum weight of the people in the last group.

The bit rows are the subsets {0, 2, 3} and {1, 4}. The first ride carries 2 + 4 + 5 = 11; the second carries 3 + 9 = 12. No single ride can carry everyone, so two rides is optimal.

We can calculate the values recursively and then apply dynamic programming. Let rides(S) be the minimum number of rides for a subset S, and last(S) the minimum weight of the last ride in such a solution. For a subset S, we go through all people in S and optimally choose the last person p to enter the elevator. Each choice yields a subproblem for a smaller subset. If last(S \ p) + weight[p] ≤ x, we can add p to the last ride. Otherwise, we reserve a new ride containing only p.

The above loop guarantees that for any two subsets S1 ⊂ S2, we process S1 before S2. Thus the dynamic programming values are calculated in the correct order.

20!≈ 2.4 × 1018permutations
220≈ 1.0 × 106subsets
pair<int,int> best[1 << N];
best[0] = {0, 0};

for (int s = 1; s < (1 << n); s++) {
  best[s] = {n + 1, 0};
  for (int p = 0; p < n; p++) {
    if (s & (1 << p)) {
      auto option = best[s ^ (1 << p)];
      if (option.second + weight[p] <= x) {
        option.second += weight[p];
      } else {
        option.first++;
        option.second = weight[p];
      }
      best[s] = min(best[s], option);
    }
  }
}

Time O(2nn) · memory O(2n)

6.2.5

Counting Tilings

Sometimes the states of a dynamic programming solution are more complex than fixed combinations of values. Consider the problem of counting the distinct ways to fill an n × m grid using 1 × 2 and 2 × 1 tiles. There are 781 ways to fill the 4 × 7 grid, one of them being the solution below.

781 tilings of 4 × 7
Each row as a string of four symbols
⊓ top of a vertical tile ⊔ bottom of a vertical tile ⊏ left half of a horizontal tile ⊐ right half of a horizontal tile

Hover or focus a row string to locate it in the drawing.

The problem can be solved with dynamic programming, row by row. Each row can be represented as a string of m characters from the set {⊓, ⊔, ⊏, ⊐}. Suppose the rows are indexed from 1 to n. Let count(k, x) denote the number of ways to construct rows 1 … k such that string x corresponds to row k. Dynamic programming applies because a row's state is constrained only by the previous row. A solution is valid if row 1 does not contain ⊔, row n does not contain ⊓, and all consecutive rows are compatible.

Since a row has m characters with four choices each, the number of distinct rows is at most 4m. We can go through the O(4m) states for each row, and for each, O(4m) states for the previous row, so the time complexity is O(n42m). In practice, rotate the grid so that the shorter side has length m, because the factor 42m dominates. The solution can be made more efficient with a more compact row representation. It suffices to know which columns of the previous row contain the upper square of a vertical tile. Thus a row needs only the characters ⊓ and □, where □ combines ⊔, ⊏, and ⊐. With this representation there are only 2m distinct rows, and the time complexity is O(n22m).

A closed form, and why it is delicate

There is also a direct formula for the number of tilings, a product over odd-indexed cosine terms:

∏a=1⌈n/2⌉ ∏b=1⌈m/2⌉ 4 ( cos2(πa / (n + 1)) + cos2(πb / (m + 1)) )

This formula is very efficient, because it calculates the number of tilings in O(nm) time, but since the answer is a product of real numbers, a problem when using the formula is how to store the intermediate results accurately.

Dynamic programming is not one algorithm. It is the habit of asking what a state is, what smaller states it depends on, and in which order they must be filled. Once those three questions have answers, the code is usually short.
