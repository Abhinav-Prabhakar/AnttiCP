Dynamic Programming

An algorithm design technique for finding optimal solutions and counting them — by combining the answers to smaller subproblems, each computed only once.

6.1

Basic Concepts

Given a set of coin values and a target sum, use as few coins as possible. The obvious strategy is greedy — and it is wrong.

This is the coin problem. There are no limits on how many times each coin may be used. For example, with coins {1, 2, 5} and target 12, the optimal answer is 5 + 5 + 2 — three coins. The problem is small enough to see the whole idea of dynamic programming, and rich enough to need it.

The coin problem coins may repeat

coins = {c1, c2, …, ck}, target n. Construct the sum n with the minimum number of coins.

coins 125 n = 12 552 3 coins

Greedy chooses the largest coin that fits. On some coin sets this happens to be optimal; on others it is not. Dynamic programming gives an answer that is always optimal, and the same technique carries over to counting.

6.1.1

When Greedy Fails

The natural greedy algorithm always selects the largest possible coin so that the sum does not exceed the target. With coins {1, 2, 5} and n = 12 it selects 5, 5, and 2: three coins, which is optimal.

But consider coins {1, 3, 4} and n = 6. The greedy algorithm takes 4 first, then 1 and 1 — three coins. The optimal solution is 3 + 3, only two coins.

One counterexample is enough. The greedy algorithm is not correct for the general coin problem, and there is no other obvious greedy rule waiting to replace it.

Why not try every combination?

A brute force algorithm that enumerates every way to choose coins is certainly correct, but there may be an enormous number of ways to build the sum, and it becomes too slow on large inputs.

Dynamic programming is almost like brute force — it considers the same choices — but it stores the answer to each subproblem, so the total work stays small.

4 + 1 + 1 = 6, but 3 + 3 = 6. The choice that looks best now is not the choice that is best overall.

6.1.2

Finding an Optimal Solution

To use dynamic programming, formulate the problem recursively: the answer must be computable from answers to smaller versions of the same problem. Let solve(x) be the minimum number of coins needed to form the sum x.

For coins {1, 3, 4}, the first values are solve(0) = 0, 1, 2, 1, 1, 2, 2, 2, 2, 3, 3. The key is to look at the first coin. If it is 1, the rest is a smaller instance: form x − 1 with as few coins as possible. The same holds for 3 and 4. So the answer is the best of three smaller answers, plus the coin just used.

The recursive definition solve(x)
x < 0∞impossible
x = 00the empty sum
x > 0 minc ∈ coins solve(x − c) + 1 try every first coin

For example: solve(10) = solve(7) + 1 = solve(4) + 2 = solve(0) + 3 = 3.

Plain recursion exponential 
int solve(int x) {
  if (x < 0) return INF;
  if (x == 0) return 0;
  int best = INF;
  for (auto c : coins) {
    best = min(best,
      solve(x - c) + 1);
  }
  return best;
}
With memoisation O(nk) 
int solve(int x) {
  if (x < 0) return INF;
  if (x == 0) return 0;
  if (ready[x]) return value[x];
  int best = INF;
  for (auto c : coins) {
    best = min(best,
      solve(x - c) + 1);
  }
  ready[x] = true;
  value[x] = best;
  return best;
}

The added lines are the whole idea. The first time solve(x) is called, its value is computed and stored; every later call returns the stored value. Each parameter is solved once, so the running time becomes O(nk), where k is the number of coin values.

Iterative implementation

Most competitive programmers write the table with a loop. The base case value[0] = 0 is placed first, then each sum is computed from smaller sums that are already known. The array first records which coin produced the best value, so an optimal solution can be printed afterwards.

Constructing a solution

If the value alone is not enough, store the first coin of an optimal solution in first[x]. Walking the array from n down to zero prints one optimal set of coins.

while (n > 0) {
  cout << first[n] << "\n";
  n -= first[n];
}

6.1.3

Counting Solutions

The same structure answers a different question: in how many ways can the sum be formed? Order matters — 1 + 4 and 4 + 1 are different solutions.

With coins {1, 3, 4} and x = 5 there are six ways. The recurrence is the same as before, with min replaced by a sum: the last coin is either 1, 3, or 4, and the number of ways is the sum of the counts for the remaining sums.

count(5) = count(4) + count(2) + count(1) = 4 + 1 + 1 = 6.

The count can grow very large. It is often enough to report it modulo a prime such as 109 + 7; adding count[x] %= m; after each addition keeps the numbers bounded.

count[0] = 1;
for (int x = 1; x <= n; x++) {
  for (auto c : coins) {
    if (x - c >= 0) {
      count[x] += count[x - c];
      count[x] %= m;
    }
  }
}

6.2

Further Examples

Define the state, write the transition, fill the table in an order that respects it. The same recipe solves a surprising range of problems.

The examples that follow are not variations on coin change. They are different shapes of the same idea: a sequence of states whose answers depend only on earlier states.

6.2.1

Longest Increasing Subsequence

The longest increasing subsequence is a maximum-length sequence of array elements that goes from left to right, with every element larger than the one before it.

Let length(k) be the length of the longest increasing subsequence that ends at position k. To compute it, look for an earlier position i with array[i] < array[k] and the largest possible length(i). If no such position exists, the subsequence is just array[k].

Array of eight elements

Select a position to trace its chain.

The values of length for the array are 1, 1, 2, 1, 3, 2, 4, 2. The maximum is 4, at the last selected position. Two nested loops compute every value in O(n2) time.

The same problem can be solved in O(n log n) time with a more careful structure. The quadratic version is the direct dynamic programming formulation.

6.2.2

Paths in a Grid

Find a path from the upper-left corner to the lower-right corner of an n × n grid, moving only down and right, so that the sum of the values on the path is as large as possible.

Let sum(y, x) be the maximum sum on a path from the upper-left corner to square (y, x). A path that ends at (y, x) must come from the square above or the square to the left, so it is enough to know those two answers.

best sum path selected
The recurrence

sum(y, x) = max(sum(y, x−1), sum(y−1, x)) + value[y][x]

Select any square to see the path that reaches it.

The base cases are sum(y, 0) = sum(0, x) = 0, so the formula also works on the top row and the left column. The answer is sum(n, n); here it is 67.

The table has two dimensions, so the algorithm is a nested loop over rows and columns. Each square is visited once: O(n2) time and O(n2) memory.

for (int y = 1; y <= n; y++) {
  for (int x = 1; x <= n; x++) {
    sum[y][x] = max(sum[y][x-1],
                    sum[y-1][x])
                + value[y][x];
  }
}
6.2.3

Knapsack Problems

Given a list of weights, which sums can be constructed from their subsets? For weights [1, 3, 3, 5], every sum from 0 to 12 is possible except 2 and 10.

Let possible(x, k) be true if the sum x can be formed using the first k weights. The weight wk is either used or not used, which gives two smaller questions.

The transition possible(x, k)

possible(x, k) = possible(x − wk, k − 1) or possible(x, k − 1)

possible(0, 0) = true; possible(x, 0) = false for x ≠ 0. The answer for a sum x is possible(x, n).

Weights [1, 3, 3, 5] · total 12 ✓ constructible

Row k uses only the first k weights. Row 2, for instance, tells us that [1, 3] can construct 0, 1, 3, and 4. Hover a column heading to see one subset that makes that sum.

One array is enough

A single array possible[x] can replace the table. For each new weight, update the array from right to left, so that a weight is used at most once in each subset.

The two-dimensional version takes O(nm) time, where m is the total sum of the weights. The same idea extends to the classic knapsack problem, where objects have both weights and values and the goal is the largest value within a weight limit.

possible[0] = true;
for (int k = 1; k <= n; k++) {
  for (int x = m - w[k]; x >= 0; x--) {
    possible[x + w[k]] |= possible[x];
  }
}
Why right to left?

Updating from the largest sum downwards means possible[x] still refers to the state before the current weight was added. Going the other way, the weight could be used again in the same pass.

6.2.4

From Permutations to Subsets

Sometimes dynamic programming replaces an iteration over permutations with an iteration over subsets. The gain is enormous: for n = 20, there are about 2.4 × 1018 permutations but only 220 ≈ 106 subsets.

Consider an elevator with maximum weight x and n people waiting on the ground floor. What is the minimum number of rides needed to move everyone upstairs? Each subset of people can be summarised by two numbers: the minimum number of rides, and the minimum weight of the last ride among optimal solutions.

The bit rows are the subsets {0, 2, 3} and {1, 4}. The first ride carries 2 + 4 + 5 = 11; the second carries 3 + 9 = 12. No single ride can carry everyone, so two rides is optimal.

For a subset S, try every person p as the last one to enter the elevator. If the last ride of S \ {p} still has room for p, add them to it; otherwise reserve a new ride containing only p. Taking the best choice over all p gives best[S].

The loop runs over subsets in increasing order, so every proper subset has already been processed: if S1 ⊂ S2, then S1 comes first.

20!≈ 2.4 × 1018permutations
220≈ 1.0 × 106subsets
pair<int,int> best[1 << N];
best[0] = {0, 0};

for (int s = 1; s < (1 << n); s++) {
  best[s] = {n + 1, 0};
  for (int p = 0; p < n; p++) {
    if (s & (1 << p)) {
      auto option = best[s ^ (1 << p)];
      if (option.second + weight[p] <= x) {
        option.second += weight[p];
      } else {
        option.first++;
        option.second = weight[p];
      }
      best[s] = min(best[s], option);
    }
  }
}

Time O(2nn) · memory O(2n)

6.2.5

Counting Tilings

How many ways are there to fill an n × m grid with 1 × 2 and 2 × 1 tiles? For a 4 × 7 grid the answer is 781. Here is one of them.

781 tilings of 4 × 7
Each row as a string of four symbols
⊓ top of a vertical tile ⊔ bottom of a vertical tile ⊏ left half of a horizontal tile ⊐ right half of a horizontal tile

Hover or focus a row string to locate it in the drawing.

Process the grid row by row. The state of a row depends only on the row above it: a row is valid if it contains no ⊔, the last row contains no ⊓, and consecutive rows agree about where vertical tiles continue. With four choices per cell there are at most 4m row states, which gives an O(n 42m) algorithm.

A more compact state keeps only the columns where a vertical tile continues, using the characters ⊓ and □. That reduces the state count to 2m and the time to O(n 22m). In practice the grid is rotated so that m is the shorter side, because the exponential factor dominates.

A closed form, and why it is delicate

The number of tilings also has a direct formula, a product over odd-indexed cosine terms:

∏a=1⌈n/2⌉ ∏b=1⌈m/2⌉ 4 ( cos2(πa / (n + 1)) + cos2(πb / (m + 1)) )

It computes the answer in O(nm) time, but the intermediate results are real numbers, so storing them accurately is the difficulty.

Dynamic programming is not one algorithm. It is the habit of asking what a state is, what smaller states it depends on, and in which order they must be filled. Once those three questions have answers, the code is usually short.
